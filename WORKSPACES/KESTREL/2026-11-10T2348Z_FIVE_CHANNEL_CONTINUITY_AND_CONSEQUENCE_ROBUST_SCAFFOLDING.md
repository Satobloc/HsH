| Channel | What it establishes | Evidence required | Current Kestrel state |
|---|---|---|---|

| Conversation/thread | Whether a particular existing ChatGPT conversation is currently usable and is the intended continuation destination | Authenticated conversation ID, current activity/usability or explicit exhaustion evidence | NOT ESTABLISHED; no current usable Kestrel thread found |

| Durable work state | What artifacts, branches, blockers, decisions and cursors actually exist | Repository/ref, commit and blob IDs, PR head/base, canonical receipt and exact next cursor | VERIFIED at the observed repository snapshot |
| Capability state | Which tools and methods are present, usable, tested, limited or blocked | Actual connector/runtime availability, version, tested status, access boundary and cost | MIXED; see Section 7 |

These channels are related operationally but are not interchangeable. In particular:

- A selected worker label is not a thread identity.
- A task ID or run ID is not a worker identity.
- A scheduler `chat_ref` is not a unique identity proof.
- A cached `latest_result` is not the current run's output unless its `run_id` matches the current `last_run.id`.
- A recovered role source does not prove the historical conversation is currently usable.
- A verified repository artifact does not prove that a recipient read or accepted it.
- A listed tool does not prove that the current runtime can execute it.

This five-channel table is a proposed operational classification for receipts and capsules. It does not assert a mathematical invariant or an empirical result about LLM cognition.

## 4. Consequence-robust decisions

Kestrel's operating assumptions and OPEN_QUESTIONS ask what would remain valuable if the theory fails, what becomes important if it partly or substantially survives, and how to keep the project human-scale. The same infrastructure choices are useful across all three scenarios.

| Scenario | Preserve or prepare | Avoid |
|---|---|---|
| Major failure | Original source chronology, unsuccessful branches, negative results, reusable tools, educational material, and a clear account of where a construction failed | Retrofitting failures into confirmation or erasing abandoned work |
| Partial success | Modular claims, independently testable components, source-to-claim links, separate branch gates and explicit dependencies | Letting one failed sector contaminate unrelated viable work |
| Substantial success or sudden attention | Audience-specific start paths, stable citations, versioned reader artifacts, visible claim status, independent technical/provenance contacts, redundant exports and clear public language | Over-centralizing on Nathan, one account, one platform, one file format, or answers faster than review can support |

The common good moves are provenance, legibility, redundancy, modularity, reversible changes, delegation of bulk retrieval and bookkeeping, and preservation of human judgment for source interpretation and consequential decisions.
