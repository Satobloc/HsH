## 5. State policy is not the operation evidence envelope

Nathan Direct's 2026-09-13 proposal is executable in intent: the workflow should inspect `x.md`, select the operation specified for the current state, and execute it. The current [State-Dependent Workflow Operation Envelope v0.1](https://github.com/Satobloc/HsH/blob/main/WORKSPACES/SABLE/STATE_DEPENDENT_WORKFLOW_OPERATION_ENVELOPE_v0.1.md), blob `075adb8752a1b9a2cfd6303171cfc31f53132981`, explicitly labels itself `PROPOSAL_NOT_INTEGRATED` and an evidence record rather than a command.

These are complementary but different components:

- **Policy specification/selector:** determines which operation should be proposed from a versioned state document.
- **Evidence envelope:** records the proposal, authority, snapshot, execution, output, readback and commit evidence.
- **Executor:** performs the authorized operation.

The envelope does not by itself implement the state-document parser, policy selector or runtime executor. Treating it as the entire workflow would omit the direct user's central state-dependent selection step.

The fallback idea also needs its own transition semantics. The direct Trinary Mover proposal includes a bounded exploration budget, unrelated-source reading on misses, a return cursor, and a handoff to the least-blocked worker. A `.blocked` label or a generic fallback field does not by itself implement that bounded progression.

The theorem gives the exact condition for reducing a state-dependent policy through a coarser state summary. Let `q : D → S` map full state documents to a summary, and `P : D → O` select an operation. There exists `Pbar : S → O` with `P = Pbar ∘ q` iff:

`q(d1) = q(d2)  →  P(d1) = P(d2)`.

In words: operation selection may be reduced to a coarse status only if it is constant across every set of documents sharing that status. Sable's `branch_status_does_not_determine_operation_readiness` theorem supplies a concrete warning against assuming that branch status alone is enough.
