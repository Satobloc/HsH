# Adaptive Collaboration Pilot — v0.1

**Status:** Active test pilot; configuration-first, manually operated, reversible.
**Created:** 2026-11-19
**Purpose:** Test a compact human–AI control surface that preserves continuity, directs attention, navigates complex plans, and improves execution without duplicating project records or imposing a rigid universal workflow.

This pilot extends, but does not replace, the Memory Credenza model, Phase Steering, Steering Charter, Three-Paper Campaign, Old Plan Recovery Sweep, BEDROCK, live task graphs, project workspaces, or protected scheduler controls.

## 1. Pilot rules

1. **The user is the directing operator.** The assistant maintains, navigates, tests, and proposes improvements; it does not silently acquire authority over priorities, ownership, conclusions, schedules, or access.
2. **The repository is durable memory; the conversation is the live interface.** Keep the conversational Key small and resolve it into this registry and authoritative project records.
3. **Do not duplicate the Castle.** This file is a router and compact plan register, not a second evidence archive or full task database.
4. **Preserve source authority.** Project-specific BEDROCK, charters, source records, task graphs, and scheduler controls remain authoritative within their scopes.
5. **Flexible ordering, explicit obligations.** Eligible work may be reprioritized. A PIN is a return obligation with a reason, dependencies or trigger, and exact resume cue; it is not a casual bookmark.
6. **No false completion.** A Tock requires a bounded operation, durable result, and recorded next cursor. A chat turn, intention, tool call, or file creation alone is not a completed work unit.
7. **Configuration before code.** Begin with a human-readable registry and router. Add scripts, samplers, or autonomous behavior only after observed need and bounded testing.
8. **No silent schedule changes.** Existing automation IDs, schedules, phases, enabled states, and worker ownership are protected unless separately and explicitly authorized.
9. **Real-data and source gates remain controlling.** In H(s)H/SAT work, preserve BEDROCK's real-world-data-first rule and prior-permission gate for data-free calculations.
10. **Test alternatives.** TICK/TOCK strings, Unicode pointers, Credenza/cubby arrangements, cube-like structures, graph queues, and other representations are candidates. None is canonical merely because it is convenient.

## 2. Architecture

### Three scales

- **KEY:** a compact boot capsule: remit, current focus, immediate next action, return locator, and Credenza version.
- **CREDENZA:** this control surface: Compass, Atlas, Work Tray, Watchtower, and purpose-specific access cards.
- **CASTLE:** the authoritative project/repository environment: source records, task graphs, issues, code, tools, methods, histories, and deliverables.

### Surface

| Element | Job |
|---|---|
| Compass | Purpose, boundaries, controlling priorities, permissions |
| Atlas | Principal projects, repositories, branches, cross-links |
| Work Tray | PIN / NOW / NEXT / RETURN |
| Watchtower | Dependencies, stale pointers, due reviews, neglected areas, blocked work |

Candidate cubbies: Evidence and provenance; Questions and hypotheses; Findings and decisions; Tools and instruments; Methods and quality controls; Entities and connections; Neglected corners; Workshop and capability development; Parking and retired work.

A cubby is an access route, not necessarily a physical folder. Each access card should expose only: purpose, authoritative route, open-when trigger, status, last meaningful inspection, and return cue.

## 3. State vocabulary

- **NOW:** the single foreground operation.
- **NEXT:** the next eligible action, not necessarily the next item in a fixed sequence.
- **PIN:** a suspended or deferred return obligation. Record why it is pinned, its return trigger/dependencies, and exact resume point.
- **RETURN:** durable source/artifact/task cursor from which the work can be verified and resumed.
- **TICK:** current place marker; not evidence of progress or completion.
- **TOCK:** bounded operation completed with a durable result and updated cursor.
- **HEARTBEAT:** meaningful human-directed activity/contact signal; not proof of substantive work.
- **BRANCH:** a separately addressable line of work spawned from another operation.
- **BLOCKED:** cannot proceed under current evidence, permissions, dependencies, or tools.
- **PARKED:** intentionally inactive, with a reason and re-entry condition.
- **RETIRED:** deliberately ended or superseded, with disposition recorded.

Do not conflate a missing result, a negative result, an unreadable source, a failed operation, and a blocked operation.

## 5. Compact addressing experiment

**No character registry is canonical yet.** The earlier illustrative string ▸a32jqjfe984 is a prototype only; its character meanings are not established.

Trial three competing representations against the same real tasks:

1. **Human-readable pin:** PIN | NOW | NEXT | RETURN.
2. **Short stable node IDs:** e.g. P-02 / NATIVE-VERIFY, resolved through this registry or a project-local task record.
3. **Compact character sequence:** one character per node/transition, with a versioned registry mapping each character to a task, sub-sequence, action, or route. Test Unicode and alphanumeric namespaces; do not assume one character must always mean one atomic action.

A compact sequence must define: namespace, registry version, current cursor, branching/conditional semantics, nested sequence behavior, escape/unknown-character handling, state transition, and durable return address. Registry meanings must never silently change across versions. A character may resolve to another sequence or module, not only a single task.

Candidate alternative structures remain open: Credenza/cubby model, cube-like spatial control surface, nested graph, decision tree, script-generated queue, or hybrid. Compare practical recovery and execution, not aesthetic preference.

## 6. First operating protocol

At the beginning of a substantial work session:

1. Read the Key and this pilot's current Work Tray.
2. Verify the NOW item's authoritative project state; never trust a stale conversational pin alone.
3. Check whether the requested work creates a branch. If so, preserve the prior PIN before switching.
4. Select one bounded operation and identify its input, output, stop condition, permission/source gates, and return locator.
5. Execute and verify the operation.
6. Record a Tock only when the durable result and next cursor exist.
7. Reconcile NEXT and PIN. Do not silently drop a return obligation.
8. At a suitable checkpoint, inspect the Watchtower for blockers, stale links, due review, and neglected work.
9. Update this router only when a plan's status, route, dependency, or next action materially changes. Detailed task progress stays in the authoritative project record.

## 7. Pilot experiments and evaluation

### Experiment A — interruption and resumption
Use the private archive corpus task as a real workflow. Record whether the system can resume the exact extraction/OCR/transcription step after a tangent or context change without repeating work or losing a dependency.

### Experiment B — branch and return
Temporarily branch from the archive task into this architecture pilot. Preserve both cursors. Verify that the pilot can be advanced without erasing the archive's next action.

### Experiment C — addressing formats
Compare human-readable pins, stable node IDs, and compact character strings on the same 5–10 bounded operations. Record successful exact resumption, ambiguity, stale-pointer errors, update effort, and token/attention cost.

### Experiment D — Credenza alternatives
Sketch at least two materially different arrangements (including a cube-like alternative if useful). Compare retrieval paths, visibility of parked work, ability to represent nested sequences, and maintenance burden. Do not force the Credenza metaphor if another structure performs better.

### Measures
- Exact-resumption success after interruption/context handoff.
- Missed, duplicated, or incorrectly resumed operations.
- Stale or ambiguous pointers.
- Time/turns required to find the authoritative task and next action.
- Number of useful discoveries from neglected-work review versus false triggers.
- Human correction rate and ease of overriding the assistant.
- Maintenance and token/attention overhead.
- Whether the structure remains understandable to a successor without the originating conversation.

Record actual trials, not predicted benefits. A null result is useful. Simplify or retire mechanisms that add ceremony without improving outcomes.
