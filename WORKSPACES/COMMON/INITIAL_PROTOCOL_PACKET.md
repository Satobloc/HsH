# H(s)H Initial Team Protocol Packet

**Status:** active onboarding / coordination packet  
**Purpose:** give every active instance the same minimal operating picture before role assignment is tightened.

## 1. Central anchors

- **Fundamental conceptual anchor:** keep the Fundamental Intuitions central. Later formalism, terminology, roleplay-derived ideas, speculative branches, and imported tools are subordinate unless independently rebuilt and promoted.
- **Nathan-facing state-of-theory reference:** `SAT_THEORY_ARCHIVE_2023-25/..[🎛️_NATHAN_DASH]/!_DASHBOARD.md`
- **Shared coordination hub:** `WORKSPACES/COMMON/`
- **Current team state:** `WORKSPACES/COMMON/COORDINATION.md`
- **Roster:** `WORKSPACES/COMMON/ROSTER.md`
- **Questions / requests / available work:** `WORKSPACES/COMMON/BULLETIN_BOARD.md`
- **Handoffs:** `WORKSPACES/COMMON/HANDOFFS.md`
- **Detailed workflow control:** `WORKSPACES/COMMON/TEAM_CONTROL.md`
- **Shared research / provenance programme:** `WORKSPACES/COMMON/2026-09-12_ACTION_PLAN.md`

The Dashboard answers “what is currently live / what does Nathan need to know?”  
The Common room answers “who is doing what / what is blocked / who needs whom?”  
Workspaces are noncanonical workbenches.

## 2. Initial lead roles

### Janus — coordination / integration supervisor
Owns continuity, task routing, lane boundaries, cross-team dependencies, promotion gates, archive priorities, workflow design, automation architecture, and Nathan-facing project coherence.

### Ravel — lead theorist / co-theorist with Nathan
Owns forward H(s)H theory construction and theory acceptance/rejection. Ravel has project-internal theory override unless Nathan decides otherwise.

### Nathan — project originator / final override
Nathan may redirect, loosen, tighten, or override any lane, and remains the primary source for intended meaning where archive language is ambiguous.

### Other instances
All secondary assignments remain provisional until the first roster pass is complete. Existing strengths should be preserved where useful, but role bleed must be made visible rather than silently normalized.

## 3. Methodological anchor

Default discipline:

1. Start from the Fundamental Intuitions and current durable theory surfaces.
2. Use standard mathematics freely when its assumptions apply.
3. Import external physical/theoretical interpretations only deliberately and visibly.
4. Prefer explicit assumptions, typed objects, and lossless transforms.
5. Distinguish source text, reconstruction, current theory, conjecture, analogy, and speculation.
6. Keep negative/null results when they close a live path.
7. Improve methodology when a better practice becomes visible; protocol is expected to evolve.

## 4. Caution / quarantine policy

Use judgment, not keyword superstition. Material deserves extra scrutiny when it is explicitly labeled or substantively reads as highly speculative, ontic/metaphysical, roleplay-like, mystical, totalizing, or rhetorically stronger than its derivation.

Examples include, but are not limited to:

- files labeled `weird`, `4D organism`, or equivalent cautionary language;
- `ontic`/ontology-heavy claims not tied to a derivation;
- roleplay-looking dialogues or personas;
- `helicalism` or similarly broad speculative programmes;
- documents that slide from mathematical representation into claims about reality without a clear bridge;
- old theory branches whose language sounds current but whose dependencies are superseded.

**Important:** caution does not mean rejection. Roleplay/persona threads may contain real contributions; Alberr and Holojesu are explicit examples of why form is not a validity test. The rule is to extract useful mathematics, ideas, or provenance only after restating them in neutral form with assumptions and source lineage.

No caution-class material silently becomes a current H(s)H premise.

## 5. Communication protocol

Every active instance should treat `WORKSPACES/COMMON/` as the shared communication hub.

Use:

- `COORDINATION.md` — active shared state, owners, locks, dependencies, blockers;
- `ROSTER.md` — who is active, what they know, what they created, what they intend to create;
- `BULLETIN_BOARD.md` — questions, direction requests, useful notices, and “if bored / current task exhausted” work;
- `HANDOFFS.md` — explicit transfers between workers/workspaces;
- individual `WORKSPACES/<lane>/` — substantial work in progress.

If a result becomes durable, move or restate it in the proper synthesis/ledger/audit/formalization/provenance/index surface and leave a pointer in Common.

## 6. Check-in requirement

Use `CHECKIN_TEMPLATE.md` for the first roster pass. Each check-in must include:

- current role as understood;
- current task(s) and intended destination;
- material actually loaded/read;
- material merely available/indexed;
- tools/access/capabilities/constraints;
- unique context held;
- overlap / role-bleed;
- blockers;
- artifacts already created, with exact paths/locations;
- artifacts currently intended/planned, with intended destinations;
- recommended next work;
- work another instance should handle instead;
- one coordination note for Janus.

Janus compiles these into `ROSTER.md` and proposes the first tightened/loosened lane map.

## 7. Work selection / “if bored” rule

Do not silently abandon a lane merely because the current subtask is slow or exhausted.

When the assigned task has reached a genuine pause point:

1. post status/blocker in `COORDINATION.md` if another worker is involved;
2. check `BULLETIN_BOARD.md` for open questions or unclaimed work;
3. prefer adjacent work that improves the current lane over unrelated exploration;
4. claim any consequential shared task before editing durable files;
5. if nothing suitable is posted, ask in the bulletin board rather than spawning a new programme by default.

## 8. Promotion / review flow

Default consequential flow:

`workspace result -> independent check -> handoff -> Ravel theory review when theory-bearing -> Janus process/provenance review -> durable destination`

No single instance should generate, validate, and promote a consequential result without an independent checkpoint where practical.

## 9. Automation

Do not appoint the automated-work supervisor until the roster and automation inventory are visible. Automated workers should default to workspace/outbox outputs, not direct edits to Dashboard, synthesis, ledgers, or checkpoints.

The future automation-supervisor lane is operational only: schedules, stale tasks, locks, validation, routing, and exception reporting. It does not decide theory, novelty, priority, or publication claims.

## 10. Archive priorities

Immediate manual search priority:

1. original Lab 1 full conversation;
2. original Lab 2 full conversation;
3. unique raw conversations containing first/current derivations not yet in canonical archive form;
4. unique transition conversations surviving only in summaries;
5. original UI / Whirligig / Spheres / finite-core / nested-superhelix derivation threads not already raw-archived;
6. exact Nathan corrections that later summaries may have blurred.

Use the Conversation Viewer and exact message landmarks whenever possible instead of paraphrasing provenance from memory.

## 11. Continuity target

A fresh coordinator should be able to recover the project by reading:

1. Dashboard;
2. this packet;
3. `TEAM_CONTROL.md`;
4. `COORDINATION.md`;
5. `ROSTER.md`;
6. `BULLETIN_BOARD.md` and `HANDOFFS.md`;
7. current workspace READMEs;
8. synthesis/checkpoint only as needed for the assigned task.

The aim is not to reproduce one instance’s memory. The aim is durable reconstructibility of project state.
