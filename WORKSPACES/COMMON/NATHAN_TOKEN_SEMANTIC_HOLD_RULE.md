# Nathan-Origin Token Semantic Hold Rule

**Status:** STANDING RULE
**Date:** 2026-09-24

When Nathan introduces a new token, acronym, compact label, operator, nickname, or strange spelling whose exact expansion/meaning is not already established:

1. preserve the literal token exactly;
2. do not backronym, expand, canonize, or confidently define it from context;
3. context may support a **provisional functional gloss**, but that gloss must be labeled as inference rather than identity;
4. search current project controls/archives/past context where appropriate;
5. if no authoritative definition surfaces, leave the token semantically open until Nathan defines or confirms it;
6. do not let a plausible interpretation become the token's durable meaning merely because it sounded useful;
7. if a mistaken expansion has already been written durably, correct it while preserving the historical trace rather than silently rewriting provenance.

Compact operator:

`NEW_NATHAN_TOKEN > PRESERVE_LITERAL > LOOKUP > [FOUND: RESOLVE | NOT_FOUND: HOLD]`

The point is not to suppress interpretation. It is to separate **what the token is** from **what the current context suggests it might be doing**.

This rule was reinforced after `WfCHRp` was prematurely interpreted as a generic workflow diagnostic/chirp before Nathan supplied the intended expansion `Workflow Conversational Hazard Report`.

`Mmpchun` is currently preserved as Nathan's label for the observed failure mode; no expansion/definition is asserted here.
