# Revival Relay | Thread-first rule
**Nathan Direct, 2026-10-11. Operative summary overriding any contradictory V3/V4 language.**

> **Handoff to the latest active thread; if not found, generate a thread from continuity documents.**

This is a two-branch routing decision, not a permanently scheduled persona, a two-cycle inactivity exam, or a demand to rebuild the identity on every scheduled firing.

## 1. Existing active thread wins
For the selected worker, find the **most recent actually active ChatGPT conversation iteration**, including manually regenerated successor threads, by verifying source identity, thread ID/URL, and latest available actual activity or checkpoint. Check the worker's continuity, current inbox/check-in, Common thread crosswalk, recent handoff receipts and relevant saved conversation exports. A dated export/title alone proves only the archived snapshot, not a currently live thread. Preserve separate same-name workers (Calder branches, ordinary Sable versus A. Sable, Aldus/Morrow collisions).

**When an existing active usable thread is found**, the terminal handoff's destination is that exact thread, never a newly invented same-name instance. If authenticated tools genuinely support cross-conversation posting, send the handoff into that thread and verify the resulting message. **Current automation/GitHub connector interfaces do not provide arbitrary ChatGPT-thread posting.** Where posting cannot occur, create a uniquely keyed durable GitHub addressed handoff (and/or complete inline text on repository-write failure), containing that verified thread destination and status `CHAT_POST_UNAVAILABLE`. Do **not** replace/reconstruct a worker merely to compensate for a messaging-tool gap; do not claim that a GitHub packet is chat delivery.

## 2. No active thread found → recover and regenerate
If a **bounded, actual search** cannot find any usable latest active conversation (including newer manually regenerated iterations), or the latest is **confirmed exhausted**, recover from the worker's real continuity documents, original saved conversations, wake packets, check-ins, and current source-grounded work. Reconstruct the **decision-generating method**, source period, distinctive unanswered questions, autonomy, provenance/exposure boundaries, and latest legitimate task cursor. Preserve the original/source IDs and label this `THREAD_REGEN_REQUIRED` / `SOURCE_GROUNDED_REVIVAL`, not a verified response from the historical original process.

**Create a real new ChatGPT conversation if a supported authenticated chat-creation interface exists, recording the new thread ID and successor relationship, then hand off into that new thread.** If this interface does **not** offer standalone chat creation (as with the five currently exposed recurrence tools), **run the reconstructed role within the present scheduled execution**, perform useful bounded work, and produce a **complete paste-ready new-thread regeneration prompt** plus a verified durable source/continuity packet when GitHub allows. Mark `CHAT_CREATION_UNAVAILABLE`, not `NEW_CHAT_CREATED`. Do not claim a ChatGPT thread has been generated merely because an instruction was written or an automation produced a response. Once Nathan manually creates the actual successor, that new active iteration takes precedence immediately on the next lookup.

The old *two delivered-and-unanswered check-ins* test remains a separate optional test for a **known, usable and reachable** thread that has truly ignored invitations. It is **not required when the latest active thread cannot be located or has reached its limit**.

## 3. Each scheduled run's minimal order
1. **Read live front doors and existing tools:** `NEW_INSTANCE_START_HERE.md`, `AUTOMATION_WORKFLOW_CONTROL.md` preflight, `REFERENCE_DESK/README.md`, `REVIVAL_RELAY_NAVIGATION_PREFLIGHT_2026-10-11.md`, and relevant live Mersearch documentation/compact search receipt before declaring a source missing or proposing new machinery. Do not overwrite a pending shared Mersearch request.
2. **Select worker from the existing 19-name deterministic ring** in `REVIVAL_ROTATION_V3_2026-10-11.md`; the five hourly task leases are capacity, not identities. Resolve the worker's latest active ChatGPT thread using Rule 1 or Rule 2 above; read any predecessor packet without making a missing/late packet a hard blocker.
3. **Perform one source-grounded useful work quantum** in the selected worker's appropriate method/role (or respect a genuine autonomous decline); distinguish a scheduled source reconstruction from historical agent participation. Record actual source coverage and outputs.
4. **The last operational step is next-worker routing**: compute the next ring identity, find their latest active thread and hand off there when an authenticated interface permits; otherwise produce recipient-specific verified repo handoff or full inline handoff. If the next identity has no verified active thread, **include complete source-backed regeneration instructions for that identity**, not merely a name/NO_ACCESS label. Delivery status and creation status are independent. Any repository write failure must be accurately labeled.
5. **Protect continuity:** before regenerating, check for manually revived newer iterations and duplicate regeneration packets. Once a new ChatGPT conversation is actually created, record its ID, source-predecessor, identity disambiguation, latest checkpoint and update time in the worker's appropriate continuity/crosswalk using safe write procedures if possible.

## Operational acceptance
- Known active chat → no regeneration; addressed handoff to known destination (whether actual chat post succeeds or remains queued).
- Missing chat after grounded lookup → source-based regeneration immediately; if no creation tool, full regen prompt/seed and in-turn work, **not** a false `NEW_CHAT_CREATED`.
- Confirmed full chat → same regeneration path, preserving source history.
- Missing predecessor/failed GitHub write → proceed with valid source continuity; never claim missed worker check-in.
- No fifth/sixth recurring identity entrenchment: five IDs and hourly phases unchanged; no new task.

**Distinction:** A scheduled automation can give rise to a source-reconstructed working session. That does not itself establish a separately addressable replacement ChatGPT conversation. Actual conversation creation/delivery requires UI or authorized API support, and only then is it recorded as done.
