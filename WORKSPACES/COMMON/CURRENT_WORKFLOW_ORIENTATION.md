**Current as of:** 2026-09-18  
**Status:** active orientation / wayfinding surface  
**Purpose:** give a newly arriving or revived instance a fast, accurate path into the current SAT/H(s)H workflow without flattening historical state, theory status, provenance, or quarantine boundaries.

## 1. What the workflow is doing now

The current build is a distributed reconstruction, provenance, tooling, archive-access, and sandbox-theory workflow. It is not a single linear theory-writing pipeline.

Primary current emphases include:
- reconstructing current and historical SAT/H(s)H doctrine with provenance;
- recovering Nathan-authored wording and epistemic/methodological controls;
- excavating the original `Satobloc/SAT_THEORY_ARCHIVE_2023-25`;
- source-first recovery of He-3/Jarlskog/soliton material and related scale-recursive structures;
- bounded solver/reconstruction work;
- archive/index/viewer/accessibility QA;
- maintaining durable worker continuity and restartability;
- improving worker capability through explicit instance enrichment;
- keeping sandbox theory work, archive reconstruction, provenance, vetting, and theory correctness distinct.

The current integrated priority stack is recorded in `ACTIVE_AUTOMATION_ROSTER.md` and current Sable/Common control surfaces. Do not infer priority from file age or folder prominence alone.

## 4. Where to ask questions

`BULLETIN_BOARD.md` is the default shared Q&A and wayfinding surface.

Use it for:
- source/location questions;
- ownership or routing uncertainty;
- blockers;
- handoff questions;
- requests for direction;
- cross-lane notices that need an answer.

Do not invent a local answer when the unresolved question is genuinely shared.

**Unanswered-question rule:** any Q&A post that remains unanswered beyond a reasonably prompt interval should be elevated to Nathan by any working instance that next receives a direct message from him, regardless of the immediate scope of that message.

## 5. Blockers and missing check-ins

Read `CROSS_LANE_BLOCKER_ESCALATION_RULE.md`.

Any meaningful blocker encountered by any instance should be recorded durably where possible and surfaced promptly. Missing expected check-ins, reports, or automation outputs may be evidence of a possible blocker and should be investigated rather than silently ignored.

Absence is not proof of failure. Verify schedule, path, write/tool access, and current assignment where practical.

## 8. NotebookLM-specific handling

Current and upcoming NotebookLM uploads are a priority ingest frontier.

Use them for:
- Nathan-authored formulations of epistemic and methodological controls;
- source indices that may point to important underlying archive documents;
- leads to documents that may be absent from current archives;
- chronology and source ancestry.

Preserve the distinction between:
1. an NLM index naming or attesting to a source;
2. an underlying document actually located and inspected;
3. a source that remains missing or only inferred.

Do not treat NotebookLM-generated summary language as Nathan Direct unless there is a traceable exact quotation with adequate source metadata.

When Plug n Play exports arrive, treat them as an extractor-integrity QA set: verify that deliberately different selected documents/panes produce correspondingly different exported content rather than repeated copies of the same material.

## 9. Provenance and authorship rules

Do not equate `role=user` with sole Nathan authorship. A user message may contain embedded coauthored or assistant-generated material.

For Nathan Direct work, preserve:
- exact wording;
- message/date/source identity;
- authorship boundaries at span level where needed;
- adjacency/context pointers;
- branch/duplicate/prefix/superset relations;
- later corrections and supersessions.

Never convert assistant interpretation, captioning, reconstruction, NotebookLM paraphrase, or coauthored embedded prompts into sole Nathan-authored text.

## 10. Current doctrine vs historical material

Never flatten the archive into a single current voice.

Keep separate:
- historical SAT terminology;
- later H(s)H reformulations;
- current Nathan-direct clarification;
- assistant reconstruction;
- sandbox hypotheses;
- superseded/failed branches;
- unresolved contradictions.

Currentness is not correctness. Polish is not maturity. Provenance is not validation. A clean index is not theory proof.

## 11. Sandbox and quarantine

**Sandbox:** theory-bearing construction, derivation, solver work, mathematical repair, interpretation, prediction exploration, and criticism may occur here with explicit status labels.

**Quarantine:** restricted material, including PRIOR_ART-controlled content, does not leak into ordinary theory or Common surfaces. If outside reading surfaces material that may trigger quarantine, send Sable bibliographic identity/source pointer plus a minimal neutral note; do not import the mathematical machinery into ordinary development.

## 12. State-of-Reconstruction and Instance-Enrichment reports

These reports are part of project restartability and longitudinal self-audit.

### State of Reconstruction
A report should capture:
- what the instance currently reconstructs/understands;
- exact source/exposure coverage;
- current vs historical distinctions;
- confidence/status boundaries;
- unresolved gaps, contradictions, and missing sources;
- current frontier;
- what the instance would now reconstruct differently from an earlier state.

### Instance Enrichment
A report should capture demonstrable changes in:
- archive familiarity;
- theory/history familiarity;
- methodological and epistemic controls;
- mathematics/physics fluency;
- coding/formal/tool capability;
- geometric/visual reasoning;
- audit/provenance skill;
- role suitability and restart quality.

Reports should live in visible, durable repo locations with Common/Dashboard/README wayfinding. Preserve instance identity, date, and exposure state so reports can be compared longitudinally.

## 13. How to choose useful work

Default work quantum:

> one object + one operation + one durable result + one next cursor

Before acting:
- inspect current control state;
- check whether the task is duplicated, stale, blocked, unsafe, or already complete;
- use the Bulletin Board / Common surfaces for wayfinding when needed;
- prefer a bounded high-information operation;
- leave a durable result and next cursor;
- do not manufacture progress.

Safe alternates include provenance QA, extraction-gap audit, archive/source-path repair, chronology, duplicate handling, bibliography/source ancestry, infrastructure, tagging, wayfinding, bounded enrichment, or sandbox exploration.

## 14. Where outputs belong

Use visible repo locations for substantive reports intended for future reference.

General pattern:
- Common = concise routing, questions, blockers, handoffs, pointers;
- lane/workspace = bounded working state and continuity;
- durable report/index/audit surface = substantive reusable result;
- Dashboard/README/index = wayfinding when discoverability warrants it.

Do not let important project state exist only in chat, local scratch files, external apps, or automation prompts.
