## Namespacing is a gate, not polish

Nathan's standing requirement to disentangle same-named constants/variables across fields must be treated as a precondition for reusable math-tool ingestion. A future `TOOLS_LIBRARY` wrapper/API should require explicit namespace/domain identity for symbols whose semantics are not globally unique. No APPROVED reference table should flatten such symbols into a shared namespace merely because their glyphs/names match.

## Recommended first library shape (not yet instantiated)

When routing permits implementation, prefer a thin registry/wrapper layer over duplication:

- `TOOLS_LIBRARY/README.md` — contract, provenance, approval levels, namespace rules.
- `TOOLS_LIBRARY/registry.*` — machine-readable tool/formalism registry pointing to existing implementations and source definitions.
- `TOOLS_LIBRARY/math/` — reusable algebra/calculus/dimensional/numerical kernels.
- `TOOLS_LIBRARY/geometry/` — exact geometry kernels and Class-P-compatible outputs.
- `TOOLS_LIBRARY/logic/` — invariant/obligation/counterexample checks.
- `TOOLS_LIBRARY/formalisms/` — adapters for project-specific named formalisms, each with namespace manifest and source identity.
- `TOOLS_LIBRARY/reference_tables/` — generated tables with explicit status (`candidate`, `checked`, `APPROVED`), tool/source versions, tolerances, seeds where relevant, and acceptance record.

The existing `tools/` tree should remain authoritative for working solver history until an explicit migration/crosswalk says otherwise.
