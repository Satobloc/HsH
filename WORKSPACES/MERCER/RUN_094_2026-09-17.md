## Finding

A complete-looking cross-conversation message-body search subsystem exists in source but is **not wired into the current production Viewer build or page**.

`tools/build_viewer_body_search.py` can build a sharded token index at `CONVERSATION_VIEWER/data/body_search/`. It is explicitly external-source-aware: ordinary HsH conversations are read from the HsH checkout, public `Satobloc/SAT_THEORY_ARCHIVE_2023-25` records are read from a supplied GLASS checkout, curated records are read from their derived Viewer copies, and private `HSH_RESOURCES` is excluded by design. It fails the build if any visible conversation cannot be read.

`CONVERSATION_VIEWER/catalog_body_search.js` expects `data/body_search/meta.json` plus token shards and augments the conversation-list filter with message-body matches.

However, current production wiring does not activate either half:
1. `CONVERSATION_VIEWER/data/` presently contains `annotations.json`, `conversations.json`, `discovered_external_conversations.json`, and `landmarks.json`; there is no committed `body_search/` directory or `meta.json`.
2. `.github/workflows/build-conversation-viewer.yml` checks out GLASS and builds/validates the catalog, but never invokes `tools/build_viewer_body_search.py` and does not publish `CONVERSATION_VIEWER/data/body_search`.
3. `CONVERSATION_VIEWER/index.html` loads annotations, Viewer, conversation-ID, Argus-followup, provenance-search, landmarks, and presentation scripts, but does not load `catalog_body_search.js`.

## Classification

Classify this as **dormant/unwired Viewer infrastructure**, not a demonstrated production regression. The current README advertises *within-conversation* search, which is a different feature; it does not presently promise cross-conversation message-body search. Therefore absence of the body-search subsystem from the live wiring is not by itself a documentation breach.

This also means Run 93's external partial-curation mismatch should not be generalized to all source-path-sensitive Viewer features: the dormant body-index builder already contains repository-aware GLASS source resolution. If this feature is revived, that source-resolution pattern is a concrete implementation precedent for external-source-aware derived processing.

## What this establishes / does not establish

Established under the named source inspection:
- body-search generator and browser module exist;
- generated body-search data is absent from current committed Viewer data;
- current Viewer workflow does not invoke/publish it;
- current Viewer page does not load its browser module;
- the generator already knows how to read canonical GLASS sources from a separate checkout.

Not established:
- that body search was previously production-active;
- that its dormant state is unintended;
- that enabling it is currently desired;
- that the generator is runtime-green against today's full catalog;
- that its token/index semantics are sufficiently selective or performant for production.
