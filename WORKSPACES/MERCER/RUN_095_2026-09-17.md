# Mercer Run 95 — Viewer runtime source-currentness / immutable-identity boundary

**Date:** 2026-09-17  
**Scope:** one bounded Viewer retrieval/navigation QA bite  
**Theory work:** none  
**Quarantine:** not accessed

## Question

After Runs 90–94 isolated external-source provenance and source-location behavior, does the currently wired Viewer runtime actually consume the generated catalog as a frozen representation of source bytes, or does it dereference mutable canonical source URLs at viewing time?

## Sources inspected

- `CONVERSATION_VIEWER/viewer.js`
- `CONVERSATION_VIEWER/conversation_ids.js`
- `CONVERSATION_VIEWER/data/conversations.json`
- `indexes/manifests/development-conversation-dates.json`
- `CONVERSATION_VIEWER/index.html` as wiring context

## Result

The currently wired Viewer is **catalog-frozen for metadata but runtime-live for conversation bytes**.

`viewer.js` loads `data/conversations.json`, but when a conversation is selected it fetches `convo.raw_url` with `cache: "no-cache"`, parses that response, and renders the resulting messages. Current internal catalog entries point `raw_url` at `raw.githubusercontent.com/Satobloc/HsH/main/...`; therefore the bytes rendered at viewing time are whatever the canonical `main` path serves then, not necessarily the bytes that existed when `data/conversations.json` was generated.

At the same time, the header/list metadata (`message_count`, dates, title/path, etc.) comes from the generated catalog. The current catalog records a `source_state_at_utc` and source-manifest generation timestamps, but sampled internal conversation records do not carry a per-source content hash. The upstream development dating manifest likewise records path/date/count/status fields rather than per-record immutable content identity.

`conversation_ids.js` independently fetches the same `convo.raw_url` to recover the source conversation UUID for display. Thus the source-ID decoration follows the runtime source bytes as well.

## What this establishes

A source file can change on `main` after Viewer catalog generation and before the next catalog rebuild. During that interval, the Viewer can render the newer source bytes while still displaying catalog metadata generated from the earlier source state. This is a **runtime currentness/reproducibility boundary** inherent in the present wiring.

This does **not** establish that such a mismatch is currently occurring for any specific conversation. It is also not automatically a defect: the page explicitly describes loading canonical archive exports on demand, so live canonical dereferencing may be intentional. The important QA distinction is that the committed catalog is not, by itself, a byte-frozen rendering manifest.

This broadens but does not erase Runs 90–92: Srena's manual external record has an additional catalog-level immutable-identity asymmetry relative to structurally discovered external records. Run 95 instead concerns the runtime behavior of the wired Viewer generally.

## Infrastructure implication

If future Viewer design needs reproducible historical rendering, it would need either commit-pinned/raw immutable URLs, runtime hash verification against a recorded identity, derived frozen copies, or an explicitly documented live-source/currentness contract. Which policy is desired is a Sable/interface-design question; no shared Viewer change was made here.

That can determine how much historical reproducibility already exists despite runtime-live dereferencing.
