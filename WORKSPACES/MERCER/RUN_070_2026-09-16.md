## Result

The current Viewer already preserves two useful identity layers, but it does **not** expose the relation layer established by Runs 54–69.

1. The generated catalog assigns each listed source a Viewer-local `id` and records title, exact source path/corpus, date range, message count, timestamp source, warnings, and source URLs. The catalog currently contains 453 conversations (439 development, 9 live, plus registered external entries).
2. `conversation_ids.js` additionally fetches a selected raw source on demand and displays its embedded ChatGPT `conversation_id` as `CID` beside the Viewer ID. This is good source-identity visibility and means the Viewer does not entirely hide repeated source conversation UUIDs.
3. However, `conversations.json` does not retain `conversation_id` or any repeated-family/relation fields. The CID is discovered only after an individual source is opened. Therefore the list/catalog cannot currently show that two or more Viewer records belong to the same source-conversation family.
4. More importantly, neither the catalog nor the current CID decoration distinguishes the Run-69 relation classes: exact byte identity, message-ID subset/superset, same-graph metadata-only, same-graph readable-text divergence, same-graph nontext-unresolved, or graph-divergent branch/snapshot relation.
5. The Viewer README's SHA-256 discovery dedup is intentionally narrower: it suppresses byte-identical cross-repo archive copies from duplicate presentation while leaving raw sources untouched. That mechanism is sound for exact-copy presentation dedup but cannot safely stand in for source-conversation ancestry/disposition.

## What this establishes

The principal Viewer provenance gap is **not absence of source conversation identity altogether**. CID is already recoverable and displayed on selection. The gap is that family membership and relation class are not first-class catalog/list metadata, so users cannot see repeated-UUID ancestry before opening records and cannot distinguish harmless exact copies/snapshots from content-divergent or branch-divergent states.

This also means the safest next design is additive rather than suppressive: expose a derived relation/family projection while retaining every currently accepted source unless an independent curation/disposition rule applies. The relation projection must not label newest/largest/LIVE as authoritative; Runs 68–69 rule those heuristics out globally.

## Workflow observation / Sable routing

A shared Viewer/catalog schema change crosses Mercer's QA lane into shared presentation/workflow design. Per current control, Mercer should not silently redesign it. Recommended Sable design question: should repeated source-conversation family/relation metadata be generated as a separate derived ledger joined by Viewer ID/source path, or added directly to `conversations.json`? A separate generated ledger has the advantage of keeping the existing catalog contract stable while the relation vocabulary matures.
