## Result
The current external-discovery implementation does **not** enrich manual registrations with `source_sha256` or another immutable source identity. Structurally discovered records are created with `source_sha256 = sha256(path)`. After discovery, the script performs an explicit merge in which `merged = list(manual["conversations"])`; the comment states that manual registrations win on ID/path, and discovered items whose ID or path collides with a manual item are skipped. The manual record is therefore passed through verbatim into `discovered_external_conversations.json` rather than reconciled/enriched from the structurally discovered copy.

`build_conversation_viewer_resolved.py` then points the base Viewer builder at that generated merged file when it exists. The workflow validates only that manual IDs reached the final catalog and that public GLASS records are external; it does not require immutable identity fields on manual registrations.

## What this establishes
This closes the Run-90 generator-intent question at implementation level: the provenance asymmetry is a direct consequence of the current **manual-wins/pass-through merge design**, not an incidental omission introduced later by the Viewer builder. The implementation deliberately preserves manual records on ID/path collision, but no inspected comment or schema statement says that missing hashes are an intended provenance policy. Therefore classify the present behavior as **implemented pass-through semantics with an unclosed reproducibility field gap**, not as evidence that manual records are formally exempt from immutable identity.

A minimal future repair could enrich a manual record from a structurally discovered same-path/same-ID record while preserving manual editorial fields, but that is a shared-schema/workflow decision and remains for Sable/interface review rather than unilateral Mercer implementation.
