## Material finding — validator contract is stale

The Viewer builder's actual contract is now explicit:

1. development and live manifest records are normalized and appended;
2. registered/discovered external records are appended;
3. **all accepted inputs are then deduplicated by exact `path`**;
4. on a duplicate path, the existing record is retained **unless the later record has `corpus == "live"`**;
5. `source_conversations_before_curation` is the length **after path deduplication**, not the sum of accepted input counts;
6. top-level `development` / `live` counts are computed from the post-dedup, post-curation Viewer records.

Therefore the validator's current `viewer.accepted_input_arithmetic` invariant is wrong for the observed six-record external surface. It sums accepted input counts and compares that raw sum directly with `source_conversations_before_curation`. In the settled Run-38 state that is 439 + 9 + 6 = 454 accepted inputs versus 453 post-dedup source conversations. The one-record difference is expected under the builder's path-dedup contract, not catalog corruption.

A second, subtler validator issue follows from the same semantics. `viewer.manifest_record_reconciliation` currently skips every development/live Viewer record whose path occurs anywhere in the external registry. But when an external record duplicates a manifest path and does **not** win the builder's path-dedup selection, the retained Viewer record may still be the manifest record. Blanket `external_paths` exclusion can therefore suppress a legitimate manifest reconciliation check.

`viewer.external_registry_reconciliation` is likewise too strong if interpreted as requiring every external registry record to survive as itself: a path-colliding external record may be intentionally shadowed by the earlier manifest record under builder precedence. Matching corpus/count can make the current check pass without establishing which source won.

## What this establishes / does not establish

Establishes:
- Run 38's 454 accepted inputs → 453 source conversations is explainable by the builder's documented-in-code exact-path deduplication stage.
- Mercer's validator needs an explicit path-precedence model before accepted-input arithmetic or external-vs-manifest source membership can be treated as a correctness check.
- The observed state is a validator-contract defect, not evidence of Viewer corruption.

Does not establish:
- which exact external record/path is the colliding one without a direct record-level comparison of the current external registry and accepted manifest records;
- whether any other duplicate paths exist in future states;
- theory correctness, authority, maturity, or currentness.
