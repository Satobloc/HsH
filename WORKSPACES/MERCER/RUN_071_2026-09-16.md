**Date:** 2026-09-16  
**Status:** QA/design proposal only; no Viewer/catalog schema change implemented  
**Authority:** non-authoritative provenance/accessibility layer; does not disposition archive sources or determine theory/currentness authority

## Operation

Specify the smallest Viewer-facing projection that can expose the repeated-conversation provenance distinctions established in Runs 54–70 without turning diagnostic relation classes into suppression or authority rules.

## Sources / coverage

Read current Common autonomy/workflow/coordination/handoff controls, `WORKSPACES/MERCER/TRIAL_CHECKPOINT.md`, the current Dashboard/Viewer directive, Conversation Viewer directory/data surfaces, and the production-green v4 identity-QA state summarized through Run 70. No quarantine-controlled material was opened.

Current Viewer state relevant to this design: each accepted source already has its own Viewer-local record and exact source path; selected raw sources expose embedded ChatGPT `conversation_id` as `CID`; repeated-family membership and pairwise relation class are not first-class list/catalog metadata. Current SHA-256 discovery dedup remains a separate byte-identical presentation mechanism.

## Minimum additive projection

Prefer a **separate generated relation sidecar**, not hand-authored fields embedded into each catalog record. This keeps the existing Viewer catalog's source/presentation role distinct from diagnostic provenance and makes stale relation data easier to reject atomically.

Proposed generated object: `CONVERSATION_VIEWER/data/conversation_relations.json` (name provisional; Sable/interface owner decides).

Minimum schema:

```json
{
  "schema_version": 1,
  "generated_at": "ISO-8601",
  "diagnostic": {
    "tool": "WORKSPACES/MERCER/diagnose_conversation_identity_duplicates_v4.py",
    "tool_commit": "<commit>",
    "source_repo_commit": "<commit>",
    "report_digest": "sha256:<digest>"
  },
  "families": {
    "<conversation_id>": {
      "members": [
        {
          "viewer_id": "<existing Viewer-local id>",
          "source_path": "<exact existing source path>"
        }
      ],
      "relations": [
        {
          "a_viewer_id": "<id>",
          "b_viewer_id": "<id>",
          "class": "<relation class>"
        }
      ]
    }
  }
}
```

### Relation vocabulary

Expose only the relation classes already supported by the all-family diagnostic:

- `exact-byte`
- `message-id-subset`
- `message-id-superset`
- `same-graph-metadata-only`
- `same-graph-readable-text-divergent`
- `same-graph-nontext-unresolved`
- `branch-snapshot-divergent`

Direction belongs only to subset/superset edges. Do **not** emit `newest`, `canonical`, `current`, `preferred`, `duplicate`, `obsolete`, `superseded`, or `authoritative` as inferred relation labels.

## Viewer presentation contract

The minimum useful UI is informational rather than ranking:

1. On a source record that belongs to a repeated CID family, show a compact neutral marker such as `Related exports: N`.
2. Opening it reveals the other accepted Viewer records in that family using their existing titles/paths and the diagnostic relation label to the selected source.
3. Each related record is navigable by existing Viewer identity/path. No source is hidden, merged, renamed, reordered, or suppressed because of the relation layer.
4. A short legend states that relation labels describe export/source structure and content comparison only; they do not determine archive disposition, conversation authority, theory correctness, or currentness.
5. If the relation sidecar's recorded source commit does not match the source state expected by the current generated Viewer build, the UI should omit or visibly mark the relation projection as stale rather than silently presenting it as current.

## Generation / validation contract

The relation sidecar should be generated from the same permitted raw inputs as the production identity diagnostic, with quarantine pruning before file access. It should join diagnostic source paths to the freshly generated Viewer catalog by exact source identity/path and existing Viewer-local ID.

Required checks before publication:

- every emitted `viewer_id` exists in the current Viewer catalog;
- every emitted `source_path` matches that Viewer record exactly;
- no family is emitted merely from title similarity;
- every relation endpoint belongs to the same embedded raw `conversation_id` family;
- relation class comes from the named diagnostic version, not UI inference;
- diagnostic/source commit and report digest are retained;
- missing/rejected/non-Viewer source members are not silently represented as Viewer entries; if full-family coverage is later desired, that requires an explicit schema extension rather than pretending they are accepted records;
- existing SHA-256 cross-repo presentation dedup remains independent.

## What this establishes

This is sufficient to make repeated-family provenance discoverable without changing archive disposition semantics. It also keeps the strongest negative result from Runs 68–69 intact: newer/larger/LIVE placement cannot be promoted into a global authority rule.

This does **not** establish that the proposed filename, UI wording, or sidecar ownership is final. Those are shared Viewer/workflow-interface decisions and should be reviewed by Sable before implementation.

## Workflow observation / Sable handoff

Recommended design direction: **compose, do not replace**. Keep `conversations.json` as the generated Viewer source catalog and add a versioned relation sidecar produced from the existing identity diagnostic. This minimizes schema coupling, allows relation QA to evolve independently, and prevents provenance diagnostics from silently becoming catalog authority.

Requested Sable decision: approve/adjust the sidecar-vs-inline architecture and identify the proper generated-owner workflow before Mercer implements any Viewer-facing change.
