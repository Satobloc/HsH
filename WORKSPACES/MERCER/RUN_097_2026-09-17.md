## Result

The extractor's `context_each_side` parameter is **chronological-list adjacency**, not conversation-graph adjacency.

Implementation sequence:
1. every nonempty message in `mapping` is flattened into `rows`;
2. `rows` is globally sorted by `(create_time is None, create_time or 0, node_id)`;
3. qualifying user-message positions are selected from that sorted list;
4. context is added by integer list position `i-context_each_side ... i+context_each_side`.

Although each emitted row preserves its `parent`, the parent relation is not consulted when choosing context. Therefore, in a branched conversation export, a neighboring timestamp can be selected as context even when it is not the target message's parent/child or same active branch.

The sampled LAB1 request uses `context_each_side: 1`, so this is not merely an unused parameter path.

## What this establishes / does not establish

**Established:** `context_each_side` currently means nearest messages in the extractor's globally time-sorted nonempty-message list.

**Not established:** that any existing retained extraction output actually contains wrong-branch context. This run did not compare a source conversation's graph against a generated extraction window. It therefore identifies a semantic QA risk / documentation precision issue, not a demonstrated corrupted extraction.

The extractor remains useful for bounded chronological recovery and preserves strong row-level identity fields (`node_id`, `message_id`, `parent`, role/author, recipient, create time, exact extracted text). Consumers should not presently interpret its surrounding rows as graph-local conversational context without an additional ancestry check.

## Capability / enrichment

Refined raw-conversation extraction QA distinction: **chronological adjacency, graph ancestry, and UI-visible branch adjacency are separate semantics**. A preserved `parent` field makes later graph validation possible but does not make a chronologically selected window branch-local.
